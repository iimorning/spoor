# 参与贡献 / Contributing

先读这个：**Spoor 由一个人维护。** 没有团队，也没有快速响应的承诺。
这份文档说明怎么和你（唯一的维护者）打交道，好让双方都不浪费时间。

项目范围和边界见 [GOVERNANCE.md](GOVERNANCE.md)，方向见 [ROADMAP.md](ROADMAP.md)。

---

## 提 issue

### Bug

请包含：

1. **版本**——桌面版的版本号，或网页版commit（`Help → About` 里能看到）
2. **操作系统**——Windows 10 / 11，浏览器版本
3. **怎么复现**——从哪一步开始、点了什么、期望什么、实际什么
4. **相关报错**——如果控制台有报错，贴出来

### 功能

说清楚**你要解决的问题**，而不是你想要的功能形态。
"读书时想标记的一段话，刷新后就没了"比"加个书签功能"更容易被接受。

范围外的想法不会被直接拒绝——它们会被写进
[ROADMAP.md](ROADMAP.md) 或者明确说明为什么不做。但 open issue 不等于排期。

### 我不做的事

| 类别 | 回应 |
|---|---|
| 账号、云同步、协作 | 不会做。这是范围决定，不是优先级问题。 |
| macOS / Linux 桌面版 | 目前不做。 |
| 商业使用授权 | 不在 issue 里谈，见 [README](../README.md#license--许可证)。 |
| 已在别的 issue 里提过 | 请在原 issue 里继续，别开新 issue（GitHub 会自动提示） |

## 提 PR

### 之前

- **改动超过 ~200 行，或动了架构**：先开 issue 讨论。维护者独自决定是否接受这个方向。
- **修 bug / 小改进**：直接提 PR，不用先问。

### 要求

```bash
npm install
npx tsc --noEmit     # src/ 必须是零错误
npx vitest run       # 新功能要有测试
npm run build        # 必须能构建
```

几条实际的：

- **测试文件**用 `tests/` 下的对应目录（`tests/utils/`、`tests/components/`…）
- **mock `lucide-react`** 用 `tests/mocks/lucideReactMock.tsx`，不要手抄图标名单，
  也不要用 Proxy 兜底——原因见该文件顶部的注释
- **不要跑全量测试来验证一个小改动**。全量约 4.5 分钟，定向跑一个文件几秒。
  时间预算见 [docs/TESTING.md](TESTING.md)
- **行尾**：仓库大部分文件是 CRLF，跟着现有文件走

### 会被拒绝的 PR

说清楚比含糊更省时间。这些基本不会合：

- 引入服务端或账号依赖（与本地优先冲突）
- 加遥测、数据上报或任何外部调用（除非是用户主动触发的功能，比如查词 API）
- 只改 UI 不改测试——新的交互需要对应的测试
- 大规模重写。它是单人维护的项目，审不动 2000 行的 diff

## 代码风格

跟着周围的代码走，不引入新的框架或状态管理库。
现有的选择（React + Dexie + Tauri）是深思熟虑的结果，
如果某个不够用，先开 issue 讨论为什么该换。

注释解释**为什么**，不解释是什么。仓库里已有的注释大多是中文，
新注释请跟着用——它们解释的是"为什么不那么写"，通常有踩坑的来由。

## 不会发生的事

需要直说：

- **没有响应时间承诺。** 维护者是单人，可能数周不回 issue。
- **没有"欢迎所有贡献"的承诺。** 大改动经常被拒绝，这是正常的。
- **贡献者不会被加进什么名单。** 你的名字会出现在 git 历史里，这就够了。
- **没有 Discord/Slack。** 用 GitHub issue 和 discussion。
