# 排查渲染类 bug 的操作手册（闪烁、抖动、重影、掉帧）

这份只讲一件事：**「看起来在闪 / 在抖 / 变了，但断言测不出、截图也抓不住」这类 bug，怎么用最少的时间定位到具体那一行。**

要先接受一个前提：这类问题的共同点是**瞬时的**——一次闪烁可能只有 100–200ms，而一次截图要 ~400ms；jsdom 里更是什么都没有（没有合成、没有光栅化）。所以「改完跑测试」那套循环在这里不成立，得换成下面三条路。

## TL;DR：先按现象选路

| 你看到的 | 先走哪条 | 关键动作 |
|---|---|---|
| 元素反复出现/消失、样式在抖 | **A 数 DOM 变更** | 打出「谁在频繁变」 |
| 一整块区域/一片文字看起来变了 | **B 小区域像素差分** | 必须带噪声底 + 活性对照 |
| 用户能看见、我本地复现不出来 | **C 让用户的浏览器自己说话** | 让他跑同一段片段并贴回输出 |

顺序不固定，也别死守一条。**本次的真实经历是：B 折腾了很久都测出 0，C 一跑就定位了**（见文末案例）。

## 片段：数 DOM 变更 + 长任务

下面这段贴进 DevTools 控制台，回车，然后在 6 秒内复现现象。它不依赖任何本地环境，可以直接发给用户。

```js
(() => {
  const root = document.querySelector('.canvas-cjk');
  if (!root) { console.warn('画布没找到'); return; }
  const label = (el) => {
    if (!el.getAttribute) return el.nodeName;
    const t = el.getAttribute('data-testid') || el.getAttribute('data-edge-btn')
      || el.getAttribute('data-edge-note') || el.getAttribute('data-edge-id');
    return t ? `[${t}]` : el.nodeName + '.' + String(el.className || '').split(' ').slice(0, 2).join('.');
  };
  const counts = new Map();
  const mo = new MutationObserver((recs) => {
    for (const r of recs) {
      const kind = r.type === 'attributes' ? 'attr:' + r.attributeName : r.type;
      const k = label(r.target) + '  ' + kind;
      counts.set(k, (counts.get(k) || 0) + 1);
    }
  });
  mo.observe(root, { attributes: true, characterData: true, childList: true, subtree: true });
  const lt = [];
  const po = new PerformanceObserver((l) => { for (const e of l.getEntries()) lt.push(Math.round(e.duration)); });
  try { po.observe({ entryTypes: ['longtask'] }); } catch (e) {}
  console.log('▶ 开始记录 6 秒，现在复现那个现象');
  setTimeout(() => {
    mo.disconnect(); po.disconnect();
    console.log('=== 变化汇总（次数 × 目标 + 类型）===');
    [...counts.entries()].sort((a, b) => b[1] - a[1]).slice(0, 30)
      .forEach(([k, v]) => console.log(`${v}×  ${k}`));
    console.log('=== 主线程长任务(ms) ===', lt.length ? lt : '无');
    console.log('=== 文字/子节点变化数 ===', [...counts.keys()].filter((k) => /characterData|childList/.test(k)).length);
  }, 6000);
})();
```

`[fb3fb53f-…]` 这种方括号里是 UUID 的，表示该元素带的是 `data-edge-btn` / `data-edge-note` / `data-edge-id`（即它的值是连线或节点的 id），不是 `data-testid`。

## 路线 A：数 DOM 变更（最便宜，先做）

判读才是重点：

| 输出 | 含义 | 接着查什么 |
|---|---|---|
| 只有 `attr:class` 在翻 | 样式在被反复切换（悬停/选中/可见性抖动） | 是哪个元素、哪个状态在翻；通常是命中区、层叠、或缺少延迟收起 |
| 有 `characterData` / `childList` | 内容或结构真的在变 | 直接定位那个元素，往 React 更新链路查 |
| `长任务` 有值 | 主线程被占住 | 时间戳和你的操作对齐，看那次渲染为什么贵 |
| 两者都空 | DOM 没动，是渲染层的事 | 走路线 B；或往合成层查（不透明背景、动画、`will-change`） |

**本次就是靠这张表一步到位的**：用户那边输出 `34× [edge-id] attr:class`、`文字/子节点变化数 0`、`长任务 无` → 立刻排除「文字被重写」和「主线程卡顿」，锁定「一个按钮的样式在一秒里翻了近 6 次」＝ 悬停抖动。

## 路线 B：小区域像素差分（本地复现时用）

四步，缺一步结论就不可信：

1. **把场景缩到最小。** 本次缩到「两张便签 + 一条线 + 100% 缩放」，其它卡片和连线全删掉。
2. **只截一小块**（截图接口的 `clip` 参数）。整页截图慢且容易超时；一块 100×60 完全够用。
3. **先取噪声底。** 同一块连拍两张，记下「静止状态下也会有的差异」。本次实测噪声底是 `0 像素 / 差值 0`；换布局后重取得过 `67 像素 / 差值 ≤2`。不取噪声底，后面所有差值都无从判断。
4. **必须有活性对照。** 再截一块「一定会变」的区域（本次是连线中点——悬停时 × 按钮会出现）。**如果对照区的差异也是 0，说明你的操作没生效，这次测量作废。**

判读阈值（本次实测标定；「文字被重新光栅化」是量级完全不同的信号）：

| 现象 | 变化像素占比 | 最大差值 |
|---|---|---|
| 噪声 | 0.2–0.4% | ≤3 |
| 一个小控件出现（× 按钮） | 约 100–170 像素 | ~190（控件是实心的） |
| 卡片文字被重画 | **39–48%** | **150–190** |

仓库里没有任何图像库，PNG 用 `node:zlib` 解（IHDR + inflate + 反 filter）即可，或者直接用能 `emitImage` 的截图靠眼判断。差多少用数字，**差在哪**要把差分图可视化出来看，比读数字快得多。

## 路线 C：让用户的浏览器自己说话

本地测不出来时，别再加深理论——把上面那段片段发给用户（它不依赖本地环境），让他复现并贴回输出。

发之前说清两件事：**在哪块区域操作**（"把鼠标移到两张卡之间的连线上并小幅晃动"）、**贴回哪几行**（"变化汇总 + 长任务 + 文字/子节点变化数"）。

为什么有效：本次本地（自动化浏览器）在完全相同的配置下量到「卡片文字 0 像素变化」，而用户那边 6 秒 34 次样式翻转。**自动化浏览器的合成/光栅路径和用户本机的 Chrome 不是同一条**，所以「我测不出来」不等于「没有」。用户那一行 `attr:class`，比在本地再猜十轮都值。

## 硬规则（都是本次踩过的）

1. **没有对照的「0 差异」不能信。** 两次把「悬停根本没生效」读成了「修好了」。任何「变好了」的结论，都要同时证明「这次操作确实发生了」——读被操作元素的 computed style（本次读 × 按钮的 `opacity`）最省事。
2. **不要拿「放慢动画」当放大镜，再把放大后的结果当结论。** 把过渡从 150ms 拉到 4s 确实能让瞬时现象可采样，但它会**制造出真实时长下不存在的重栅格化**。它能用来定性（"这类动画会不会引起重画"），不能用来判定"修好了没有"；用它做 A/B 时基线也必须是干净的。
3. **静止态也会有差异**（动画、亚像素、光标），噪声底每轮重取，不要复用上一轮的。
4. **注入的调试样式用完必须删干净。** 本次漏删了一个慢速过渡样式，导致后面一轮 A/B 的"闲置"基线其实是**已经被翻转过的光栅状态**，读出了完全相反的结论。
5. **截图慢（~400ms/张）且会超时。** 一轮里别排十几张；超时了不要立刻重试同一张，先换更小的 clip 或等一下。
6. **命中区随缩放变。** 连线的命中带宽是 20 世界像素（54% 缩放下只剩 ~11 屏幕像素）。量"能不能点到"要用 `elementFromPoint` 扫偏移，不要靠猜坐标。
7. **对同一坐标重复 move 不产生事件**；要偏移 2–3px 才会。悬停/点击是否生效必须单独验证（见第 1 条）。
8. **先量层叠，再改层叠。** 判断"谁盖住谁"要读 `z-index` + `elementFromPoint`，不要看 JSX 顺序——这个画布里卡片的 `z-index` 是逐节点存的（11–40 都有），和控件层谁在上面不是一眼能看出来的。
9. **抬高一层之前，先想它隐藏时会不会抢点击。** 把某个层抬到卡片之上后，顺手检查它不可见时是否还吃点击。本次的备注 chip 就是：抬高之后，一个看不见的输入框开始抢本该落在卡片上的点击。

## 本次案例（可以当模板照做一遍）

现象：悬停两张卡之间的连线时，**卡片上的文字闪烁**；只在两张卡挨得很近时出现；100% 缩放也有；Chrome。

1. 数 DOM 变更 → 本地复现出「一次抖动 7 次样式翻转」，`characterData`/`childList` 为 0，无长任务 → 排除内容更新和主线程卡顿。
2. 小区域像素差分（带噪声底 + 活性对照）→ 确认被重画的是**文字**（39–48% 像素、差值 150+），并且**控件本身出现**就会造成约 100–170 像素的变化。
3. 逐项排查触发源 → 收敛到「连线控件在动画」这一类；把 `scale` 动画去掉后本地测到 0 差异。
4. 但用户说还闪 → 本地测不出来（合成路径不同）→ **路线 C**：让用户跑片段 → `34× attr:class`、同一个按钮、6 秒。
5. 结论：控件在**狭窄缝隙里被卡片压住**（那个卡片的 `z-index` 高于控件层），鼠标只能扫到 1px 的缝，悬停一秒断 6 次；每次断开/接通都让 Chromium 重画附近图块里的字形。
6. 修复：悬停延迟收起（迟滞）+ 控件层抬到卡片之上 + 控件不再做缩放/淡入（只留颜色过渡）。
7. 验证：样式翻转 7→1、13→1；真实点击走通删除与备注编辑；像素差回到噪声底；全量测试与 HEAD 一致。

顺带一条经验：**「整片都闪」和「只有相邻的闪」往往不是同一个原因**。前者是全局性的（状态上提导致整树重渲染、整层重光栅化），后者是几何性的（窄缝里的命中区抖动）。用户报告从「一大堆卡片」变成「只有相邻卡片」时，说明第一个原因已经修掉了，别把两个当成同一个。
