# 治理说明 / Governance

这份文档说明 Spoor 由谁维护、决定怎么做、以及明确不做什么。

写它的目的不是显得规范，而是让任何人在投入时间之前就知道会遇到什么。

---

## 一句话

**Spoor 由一个人维护。** 没有团队、没有公司资助、没有路线图上的季度指标。
这是单人项目应有的样子，所以这里写的是单人项目能兑现的承诺。

---

| | |
|---|---|
| 维护者 | [@iimorning](https://github.com/iimorning)（唯一提交者） |

包括它可能数月没有新版本，以及 issues 可能长时间无人回复。

## 项目范围

### 这个项目是什么

一个**本地的阅读与批注工具**：导入 PDF 或 EPUB，和书里的内容对话，标注高亮，划词翻译，
把值得留下的段落摘成画布上的卡片。

数据留在你自己的设备上（IndexedDB），API 密钥只存在本地设置里。

### 这个项目不是什么

明确不做的事，以及不做的原因：

| 不做 | 原因 |
|---|---|
| **服务端与账号系统** | 这个项目的前提是数据不离开设备。加账号体系意味着要维护服务器、数据库和一条安全边界，而那正是它要避免的东西。 |
| **实时协作** | 同上。协作天然要求服务端与冲突合并，是另一个产品的问题。 |
| **macOS / Linux 桌面版** | 桌面端目前只打包 Windows（NSIS）。桌面壳里包含本地推理和语音代理，这些在别的平台还没有验证过。与其发一个跑不动的安装包，不如不发。 |
| **内置模型托管** | 不代跑模型。用户填自己的 API 密钥，或在桌面端接本地 GGUF。 |
| **移动端 App** | 现有的 Pocket 功能在桌面端和网页端里。做一个真正的移动端是另一个项目的工作量。 |

### 边界为什么会变

会变，但会公开说明。任何范围调整都会写在
[ROADMAP.md](ROADMAP.md) 里，并说明为什么。

---

## 决策怎么做

维护者独自决策。没有投票，没有 RFC 流程，没有路线图委员会。

这意味着：

- 讨论不等于承诺。提一个想法不等于它会被接受。
- 拒绝一个提议不需要额外理由，但通常会说明为什么。
- 方向变化会在 [ROADMAP.md](ROADMAP.md) 里留下记录，而不是悄悄发生。

---

## 怎么参与

见 [CONTRIBUTING.md](CONTRIBUTING.md)。简短版：

- **报告 bug**：开 issue，说清操作系统、版本、以及怎么复现。
- **提 PR**：先开 issue 讨论大的改动。小修复可以直接 PR。
- **不要期待快速响应。** 这是单人维护，没有 SLA。

---

## 安全问题

不要开公开 issue。走 GitHub 的 private vulnerability reporting
（如果该功能未启用，请通过
[@iimorning](https://github.com/iimorning) 私下联系）。
